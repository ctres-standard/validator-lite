# Changelog

Versions follow `MAJOR.MINOR.PATCH`, where `MAJOR.MINOR` is the version of the Standard implemented. See [CONTRIBUTING.md](CONTRIBUTING.md#versioning).

## 1.1.0 — 5 November 2026

Implements CTRES v1.1: the record model of v1.0 extended for gaming revenue and the operator's levy, the conformance levels of §10 defined by scope, the bet event R15 (the Wagering module) and the streaming mode of §8.4, in which the same records travel as a stream of events with a checkpoint per gaming day while the period package remains the signed close of the period. A package produced under 1.0 is validated unchanged and keeps `standard_version` `1.0`.

### Added

* Record types R13 Gaming Revenue Statement and R14 Venue Count (§4.13, §4.14). STR-04 to STR-07 apply to them as to every record type, including the R14 condition that a row carries either `gaming_day` or `period_start` and `period_end`; STR-08 applies the 1.1 manifest schema, under which a package that lists an R13, R14 or R15 file declares `standard_version` `1.1`.
* Record type R15 Bet Event (§4.15), file `R15_bet_events.jsonl`, the final state of each bet in a package. STR-04 reports the conditions of the schema, a settled, void or cashed-out bet without `settled_at`, a void bet without `void_reason`, an open bet with either, and an open bet whose `winnings` are not zero, the last in the schema's own words (`winnings is absent or zero while status is open`, carried by the schema as `x-ctres-message`). No conformance level requires R15. Referential check REF-14 (§4.15; §4.1): every R15 `venue_id` is carried by an R1 location, resolved by level as REF-11 resolves a venue count's venue.
* `ctres-validate --stream EVENTS`: the stream checks STM-01 to STM-07 (§8.4) over an NDJSON events file. STM-01, every line is a valid event envelope (validated without its record), a checkpoint event with `op` `create`; STM-02, sequences strictly increasing per stream without gaps, the missing range in the message; STM-03, a repeated `(stream_id, sequence)` is advisory with identical bytes (a redelivery, ignored) and blocking with different bytes; STM-04, the record validates against the schema of its `record_type`, the checkpoint against the checkpoint schema, a void carries the record's identifier; STM-05, each checkpoint's `event_count`, range and `chain_hash` (the SHA-256 of the covered lines as transmitted, each followed by a line feed, checkpoint events excluded) match the stream, and a day with events but no checkpoint is advisory; STM-06, advisory, an update or void names a record an earlier event created; STM-07, with `--max-latency DURATION` (an ISO 8601 duration in weeks, days, hours, minutes and seconds), each event is emitted within the maximum after its anchor (R3 `credited_at`; R4 `paid_at`, else `requested_at`; R5 `performed_at`; R6 `executed_at`; R8 `raised_at`; R9 `detected_at`; R15 `settled_at` where reported, else `placed_at`; snapshots `period_end`), not run without the option. The result carries a `stream` object (path, SHA-256 of the file, lines, events, checkpoints, per-stream ranges, record types, maximum latency) in place of the package keys; the text report prints the events, streams and checkpoints in the header and the result line. `validate_stream()` is the library entry point.
* `ctres-validate <package_dir> --reconcile EVENTS`: the package checks, the stream checks over `EVENTS`, and the reconciliation checks REC-01 to REC-04 (§8.4; §11), all blocking: REC-01, every record whose final streamed state is live is in the package (an R13 interim statement is superseded by the period statement and noted; a streamed type the package does not carry is advisory where the level does not require it, noted otherwise); REC-02, every package record of a streamed type was streamed (a type the stream does not carry is noted); REC-03, each package record equals its final streamed state field by field, the differing fields named with both values, and a record the stream withdrew is not in the package; REC-04, the manifest's `stream_checkpoints` are the stream's checkpoints, matched by stream and range and compared field by field. The JSON output carries the classes `stream` and `reconciliation` alongside `structural` and `referential`; the result line states the stream reconciled with.
* `demo/stream/events.ndjson`, the stream of the gaming day 14 November 2026 for the demonstration operator (26 events: six R5 checks, four R3 deposits, two R4 withdrawals, ten R15 events for seven bets, among them an update to settled, a void and a cash-out, an R13 interim statement at noon, the day's two R13 period statements, and the checkpoint), and `demo/stream/package`, the level_2 package of that day (R3, R4, R7, R13, R15 and the checkpoint in `stream_checkpoints`), both written by `scripts/make_demo.py` from the same synthetic data. `--stream` passes with no findings (and with `--max-latency PT60S`); `--reconcile` passes with seven advisory findings, the level_2 references and the R5 checks the package does not carry.
* `scripts/sync_schema.py` copies `schema/stream/*.schema.json` as well, refuses a release that lacks the stream schemas, and leaves `stream/openapi.yaml` out; the bundled schema is 22 files, and the package data includes `schema/stream/`.
* Referential checks REF-09 to REF-13: every R13 statement period and every R14 gaming day or period lies within the manifest period (REF-09); a correction names the statement it replaces, another statement of the same line where the package carries it, and is noted, not reported, where the statement may belong to an earlier package (REF-10); a venue count cites a venue an R1 location carries and banks its drop to an R6 movement or an R1 location (REF-11); an authority figure cites a report reference in R12 (REF-12); and, advisory, `ggr_declared` follows the formula the statement names, `all_in` or `cash_only`, on the statement's own fields, in exact decimal arithmetic (REF-13). REF-09 is not run when REF-07 is not run.
* Structural check STR-09 (§10; Annex D): every record type the declared conformance level requires is listed in the manifest, one finding per missing type, and R14 at `level_2` and above where any R13 line has `channel` `venue`. The levels are defined by scope: `level_1` Return (R13), `level_2` Evidence (+ R3, R4, R7), `level_3` Custody (+ R1, R2, R6, R10, R11), `level_4` Supervision (+ R5, R8, R9, R12); any record type may be included at any level. Where the manifest declares no level, STR-09 is not run and says so in a note. In a package that declares `standard_version` `1.0`, `conformance_level_declared` keeps its v1.0 meaning, a delivery level: STR-09 is not run and references are resolved as before.
* References resolved by level (§10): a reference to a record type the declared level does not require and the package does not carry is reported as one advisory finding per field and check, for example `instrument_id — not resolved: R2 is not required at level_2 and is not in the package`, by REF-01, REF-02, REF-03, REF-05, REF-06, REF-08, REF-11 and REF-12. Where the type's file is in the package the reference is blocking as before, and where no level is declared, or the level requires the type, the check notes the unresolved reference as before. Each finding in the JSON output now carries its own `severity`, `blocking_findings` and `advisory_findings` count findings by it, and the text report shows a check whose findings are all advisory as advisory.
* The result line of the text report states the declared level, `declared level_2 (Evidence)`, or `level not declared`; the JSON output's `manifest` carries `conformance_level_declared`.
* `demo/clean` is a 1.1 package declaring `level_4`: 74 records across R1 to R14, with two online gaming revenue lines whose GGR is the sum swept to the operational account, the venue line of a land-based venue, and one gaming day's count there with the cage float in R1. `demo/level1` (the manifest and R13, `level_1`) and `demo/level2` (R3, R4, R7, R13 and R14, `level_2`) are the same data cut down to the record types their level requires; both pass, with one and ten advisory findings for references the level does not resolve. `demo/defects` adds one defect for each of REF-09, REF-10, REF-12 and REF-13. The clean 1.0 package of release 1.0.1 is kept unchanged under `tests/fixtures/clean_1_0`, and the tests show that it passes.
* STR-04 states in words that exactly one of two sets of fields is required, as on an R14 row, instead of quoting the record.

### Changed

* Bundled schema 1.1.0: 22 schemas, `$id` under `https://ctres.org/schema/1.1/`, among them `records/r15_bet_event.schema.json`, `stream/event.schema.json` and `stream/checkpoint.schema.json`. `STANDARD_VERSION` is `1.1`, and the `standard_version` of the JSON output says so. Among the conditions of that release which STR-04 and STR-05 report: a slot row's meters unless `meter_source` is `not_recorded`, the drop and fills of a slot row that wins by `slot_drop_formula`, a `win_formula` that fits the unit type, and `bonus_granted` and `bonus_expired` behind `stakes_bonus` or `winnings_bonus`; R13 carries `venue_id` and `player_location`, `stakes_basis` accepts `accrual_at_result` and `statement_kind` accepts `interim`; the manifest's `conformance_level_declared` is `level_1` to `level_4` and it may list `stream_checkpoints`.
* The checks of a package are 23: STR-01 to STR-09 and REF-01 to REF-14. A finding's `field` inside a stream event is prefixed `record/`. `describe()` prints a schema's `x-ctres-message` where one is given.
* The former `level_1` to `level_3` of v1.0 (Records, Structured, Continuous) described delivery maturity and are replaced by the scope levels of §10; delivery is the manifest `submission_mode` of §8.1, which validator-lite does not test.
* The `not_checked` text, and the README, name what stays with the conformance suite: the money bridge of §4.13 between R13 and R3, R4 and R7; the agreement of R14 counts with the R13 venue line and with the bankings in R6 and R7; the agreement of R13 lines with the R15 bets behind them; whether `jurisdiction_category` is in the profile's taxonomy; and, for a stream, the latency of each record type against the profile's own parameter.
* The demonstration profile is XJ-EXAMPLE 1.1.0 (fictional). R13 records in the demonstration packages carry the core fields of §4.13 first, as the schema lists them.

## 1.0.0 — 2026-10-05

Draft for consultation. First release, implementing the Structural and Referential classes of §11 of CTRES v1.0, universal edition (2 October 2026).

### Added

* Structural checks STR-01 to STR-08: files present, SHA-256 and record counts as in the manifest, records valid against the schema of their record type, enumerations, decimal strings, timestamps with an explicit offset and real calendar dates, record identifiers unique within each record type, and a valid manifest.
* Referential checks REF-01 to REF-08: funds locations and movement sides, check decisions and supersession, instruments, single booking of each rail reference, providers, links from statements, exceptions, incidents and report references, transactions inside the manifest period (advisory), and provider attestations.
* `ctres-validate` command: a text report grouped by class, JSON output with `--json`, the package fingerprint, and exit status 0, 1 or 2.
* A copy of the CTRES JSON Schema, release 1.0.0, and `scripts/sync_schema.py` to update it.
* Synthetic demonstration packages `demo/clean` and `demo/defects`, generated by `scripts/make_demo.py`.
* Tests using the standard library `unittest` module, and a GitHub Actions workflow that runs them.
